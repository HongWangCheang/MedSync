# MedSync 开发计划

> 弱网环境下端云协同的用药管理多智能体系统（客户端：Android / iOS / 桌面）
> 核心命题：**Agent 有副作用的操作，在断网、超时、重试、进程被杀、LLM 重新推理的情况下，端到端只执行一次；排队期间情况变了，能被拦下来。**

---

## 0. 一句话架构

```
┌──── 客户端：Android / iOS / 桌面（KMP 共享代码）────┐
│ 路由 Agent（端侧小模型）  危险信号 Agent（规则优先） │
│ 记录 Agent（确定性工具）                            │
│        │ 生成 Plan（带 step_key 的动作 DAG）          │
│        ▼                                            │
│  Room：action_outbox ──WorkManager 按拓扑序上传──┐  │
└──────────────────────────────────────────────────┼──┘
                                   ① 设备→网关     │  ← Toxiproxy 注入故障
┌─────── Spring Boot 同步网关（MedTrack 现有服务端） ─▼──┐
│ 幂等入口（step_key + 载荷指纹） action_ledger  revision │
└──────────────────────────────────────────────────┬──┘
                                   ② 网关→Agent     │  ← Toxiproxy
┌──────── Python Agent 服务（FastAPI + LangGraph） ──▼──┐
│ revalidate → 药学 Agent(RAG) → 安全审核 → executor     │
│ PostgresSaver checkpointer · interrupt() 让用户确认    │
│ 工具通过 MCP Server 暴露，executor 查 tool_ledger      │
└──────────────────────────────────────────────────┬──┘
                                   ③ Agent→外部工具 │  ← Toxiproxy
┌──────── 模拟外部系统（会统计副作用次数） ─────────▼──┐
│ 医院预约 mock（号源会被抢光）  通知 mock（记录每次发送）│
└──────────────────────────────────────────────────────┘
```

**为什么分三跳**：MedTrack 现在的"请求 UUID + 载荷指纹"只保护了第①跳。第②③跳里，云端 LLM 超时重试时会**重新推理、生成参数不同的新调用**，请求级幂等就失效了。本项目要证明的是：**只有把逻辑步骤键（step_key）贯穿三跳，才能真正做到端到端只执行一次。**这也是简历和面试里最核心的一句话。

## 2. 技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 客户端 | **Kotlin Multiplatform + Compose Multiplatform**：Android、iOS、桌面（macOS/Windows/Linux）共用一套业务逻辑和界面；Room KMP 做 outbox；Ktor 做网络 | 你熟悉 Kotlin，MedTrack 的 Room 思路可以直接搬过来；同步逻辑只写一遍、只测一遍 |
| 后台调度 | Android：WorkManager；iOS：BGTaskScheduler（待做）；桌面：协程定时循环 | 各平台只决定**什么时候**调用共享的 `SyncEngine.drainOnce()` |
| 端侧模型 | LiteRT-LM + **FunctionGemma（270M）**；备选 Gemma 3n E2B / Qwen 小模型 | Android 和桌面直接用 LiteRT-LM 的 Kotlin API（支持 Android 和 JVM）；iOS 用它的 Swift API，在 Swift 里实现共享模块定义的 `OnDeviceRouter` 接口再注入。⚠️ 中文效果未验证，第 2 期先做小样本测试 |
| 同步网关 | Spring Boot + MySQL（沿用） | 已有幂等、`SELECT … FOR UPDATE`、revision、游标分页，只需扩展 ledger |
| Agent 服务 | Python 3.11 + FastAPI + LangGraph + PostgresSaver | JD 里 LangGraph 出现频率最高；checkpointer 给出 durable execution |
| 工具层 | MCP Server（FastMCP） | JD 高频词；工具和 Agent 解耦，以后 Claude 或 Cursor 也能直接调用 |
| 检索 | 沿用 MedTrack 的 BM25（SQLite FTS5）+ BGE + RRF | 已有评测结论，可以直接复用 |
| 云端 LLM | 沿用 Gemini（或任意便宜模型） | 跑评测时注意控制成本，见第 6 节 |
| 部署 | Docker Compose（MySQL、Postgres、Toxiproxy、Langfuse、gateway、agent、mocks） | 一条命令拉起全部环境，README 里写清楚 |

## 3. 核心数据结构（先把这些设计好，后面的开发都围绕它们）

### 3.1 端侧 `action_outbox`（Room KMP，三端同一张表）

| 字段 | 说明 |
|---|---|
| `action_id` | UUID，每个动作唯一 |
| `plan_id` | 同一句用户话生成的一组动作共享 |
| `step_key` | **核心字段**，= `sha256(device_id ‖ plan_id ‖ step_index ‖ tool ‖ canonical(identity_args))`，在**规划时生成，执行前已落库** |
| `identity_args` | 决定"是不是同一件事"的业务参数，例如预约用的 `patient_id + 科室 + 日期`；不包含备注这类自由文本 |
| `payload` / `payload_hash` | 完整参数及其指纹 |
| `depends_on` | 依赖的 `action_id` 列表，组成 DAG |
| `tool_class` | `READ` / `WRITE_IDEMPOTENT` / `IRREVERSIBLE` |
| `preconditions` | 规划时观察到的状态快照，例如 `{slot_version: 12, medlist_rev: 40, tool_schema: "book_appointment@v2"}` |
| `ttl` | 过期时间。例如"通知家属头晕"在 6 小时后发出去已经没有意义，必须重新确认 |
| `state` | 状态机，见下方 |
| `attempt` / `next_retry_at` | 沿用 MedTrack 的指数退避 |

**状态机**：
```
PENDING → SENDING → ACKED → DONE
            │          └→ NEEDS_USER（过期或冲突，等用户确认）→ PENDING / CANCELLED
            └→ RETRY_WAIT（网络错误、超时、5xx）→ SENDING
BLOCKED（父动作未完成）→ PENDING
父动作 FAILED 或 CANCELLED → 子动作级联变成 NEEDS_USER，不自动执行
```

### 3.2 网关 `action_ledger`（MySQL）

- 唯一键 `step_key`。
- 同一个 `step_key`、同样的 `payload_hash` → 直接返回已有结果（重放）。
- 同一个 `step_key`、不同的 `payload_hash` → **409**（沿用 MedTrack 的语义）。
- 记录 `status`、`result`、`revision`、`agent_thread_id`。

### 3.3 Agent 侧 `tool_ledger`（Postgres）

- 唯一键 `(step_key, tool)`。executor 调用外部工具前**先写一条 `INTENT`，调用成功后改成 `COMMITTED`**。
- LLM 重试时即使生成了新的参数，只要 `step_key` 已经是 `COMMITTED` 就**返回缓存结果，不再调用外部系统**。
- `step_key` 是 `INTENT` 但状态未知（例如调用时超时），先去外部系统**按 step_key 查询**确认是否已生效，再决定是否重试。模拟外部系统要提供这个查询接口。

### 3.4 降级矩阵（离线时每个能力的行为）

| 能力 | 离线 | 弱网 | 在线 |
|---|---|---|---|
| 危险信号识别 | ✅ 本地完成（规则优先） | ✅ | ✅ |
| 记服药、记症状、提醒 | ✅ 本地落库，排队同步 | ✅ | ✅ |
| 用药问答（说明书） | ❌ **拒答**，提示联网后再问 | ⏳ 排队 | ✅ 带引用回答 |
| 预约复诊 | ⏳ 排队，联网后复核 | ⏳ | ✅ |
| 通知家属 | ⏳ 排队 + TTL | ⏳ | ✅ |
| 相互作用检查 | ⏳ 联网后补查 | ⏳ | ✅ |

面试一定会问"为什么离线时不让端侧模型回答用药问题"。答案：小模型没有检索证据，答错的代价远高于暂时不答。

## 6. 评测设计细节

| 指标 | 定义 | 怎么测 |
|---|---|---|
| IVR | 重复副作用次数 / 副作用意图总数 | 以模拟外部系统 `/metrics/side_effects` 的计数为准，不依赖 App 自己上报 |
| 过期动作拦截率 | 排队期间前提条件已失效、且被正确拦下的动作 / 所有前提已失效的动作 | 用 mock 的管理接口在离线窗口内抢光号源、修改用药清单 |
| 误拦率 | 前提条件其实仍然有效、却被拦下的动作比例 | 拦截率要和误拦率一起报告 |
| 离线任务最终完成率 | 离线时发起、联网后最终正确完成（或正确转给用户确认）的比例 | 场景脚本 |
| 危险信号召回率 / 误报率 | 标准分类指标 | 约 100 条标注集 |
| 路由准确率 | 工具选择 + 参数完全正确的比例 | 200–300 条标注集 |
| 端侧延迟 | P50/P95，并注明机型 | 真机 |
| 引用正确率 | 沿用 MedTrack 的定义 | 50 题固定集 |

**控制成本的做法**：基础设施类故障（超时、断连、杀进程）用**确定性的 mock LLM** 大批量跑，比如 40 个场景 × 6 种故障 × 5 次重复。"LLM 重新推理导致参数变化"这一类，用真实 LLM 跑一个小子集，temperature 设大于 0。报告里把两部分分开写。

## 8. 面试高频追问（边做边准备答案）

1. **为什么不直接用 Temporal 或 DBOS？** 它们解决的是服务端工作流的持久执行，但**端侧离线排队、LLM 重新推理导致参数变化、排队期间前提失效**这三件事不在它们的范围内。另外项目需要能在手机上运行的组件。
2. **step_key 为什么不直接用 LLM 输出的参数做哈希？** 因为 LLM 重试时参数会变，比如备注写法不同、时间格式不同。所以要区分 identity_args 和自由文本。
3. **"服务端已经提交、客户端超时"时怎么处理？** 这是 MedTrack 已经测过的场景，现在扩展到第③跳：tool_ledger 处于 INTENT 状态时，先按 step_key 去外部系统查询，再决定是否重试。
4. **外部系统不支持按 step_key 查询怎么办？** 退化为"最多执行一次"加人工确认，并说明这是一个权衡。
5. **过期复核会不会拦得太多？** 用误拦率来回答，并说明阈值或规则是怎么调的。
6. **离线时为什么不让端侧模型回答用药问题？** 没有检索证据，答错的代价高。用降级矩阵来回答。
7. **危险信号为什么规则优先？** 医疗安全场景要求可解释、可审计，而且召回率比准确率更重要。
8. **LangGraph 的 interrupt 是怎么恢复的？** 状态存在 checkpointer 里，用 `Command(resume=)` 恢复执行；不要在 interrupt 外面套非确定性的循环。

## 9. 简历条目模板（数字留空，做完后填实测值）

> **MedSync——弱网环境下端云协同的用药管理多智能体系统**　｜　单人项目
> 技术栈：Kotlin Multiplatform · Compose Multiplatform · Room · LiteRT-LM · Spring Boot · MySQL · LangGraph · MCP · Postgres · Toxiproxy
> 项目介绍：针对医疗场景中网络不稳定时，Agent 工具调用会重复执行、执行过期动作或彼此冲突的问题，构建"端侧路由与危险信号识别 + 云端药学与安全审核"的多智能体架构，保证有副作用的操作端到端只执行一次。
>
> - **三跳幂等**：规划时生成逻辑步骤键（step_key）并先落库，贯穿设备→网关→Agent→外部工具三跳；executor 采用 INTENT/COMMITTED 双阶段记账，状态未知时先按键查询外部系统。在 [N] 次故障注入实验中，IVR 从朴素方案的 [X]%、请求级幂等的 [Y]% 降到 [Z]%。
> - **过期动作复核**：每个动作携带前提条件快照和 TTL，联网后由 revalidate 节点比对，失效时通过 LangGraph `interrupt()` 让用户确认替代方案；拦截率 [A]%，误拦率 [B]%。
> - **端侧路由**：用 LiteRT-LM 运行 [模型名]，在 [N] 条中文话术上的工具调用准确率为 [X]%，P95 延迟 [Y] ms（[机型]）；危险信号规则优先，召回率 [Z]%。
> - **多 Agent 协作**：离线生成的动作按 DAG 拓扑序执行，父动作失败时子动作级联挂起；安全审核 Agent 在不可逆动作前检查相互作用，提醒附说明书原文引用。
> - **故障注入**：用 Toxiproxy 在三跳上分别注入超时、断连、延迟，配合杀进程，构建 [N] 个场景 × [M] 种故障的可复现评测矩阵。

## 10. 风险与应对

| 风险 | 应对 |
|---|---|
| FunctionGemma 中文效果差 | 第 2 期第一步就做小样本测试，不行换 Gemma 3n 或 Qwen；最坏情况保留规则加小分类器作为路由 |
| 没有 Android 真机 | 桌面端本身就是一个"端"，可以直接在桌面端跑 LiteRT-LM；简历上如实写测试设备 |
| 本机没装 Xcode | iOS 代码已写好但还没编译验证；装好 Xcode 后先跑一次 `iosApp`，再补 BGTaskScheduler |
| 三端行为不一致 | 业务逻辑全部放在 `shared` 并用 `jvmTest` 测；平台代码只负责数据库路径、调度和端侧模型 |
| 时间不够 | 只保证第 1 期完整，第 2、3 期按优先级取舍 |
| DDInter 2.0 拿不到批量数据 | 用 openFDA 的 `drug_interactions` 章节，或只覆盖 20–30 组常见高风险组合 |
| 被质疑"做诊断" | 范围限定为用药管理和就医协同；危险信号只提示就医，App 里加免责声明 |
| LLM 评测成本 | 基础设施故障用 mock LLM 跑，真实 LLM 只跑一个小子集 |
