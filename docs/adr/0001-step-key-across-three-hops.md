# 0001 一个 step_key 贯穿三跳

状态：已采用

## 背景

MedTrack 原来的同步用"请求 UUID + 载荷指纹"做幂等，只保护了设备到服务器这一跳。加上 Agent 之后，一个动作要经过三跳：设备→网关→Agent→外部系统。

第②③跳上的重试，来源不止设备：
- 网关会重派
- Agent 进程会被杀后恢复
- LLM 超时后会重新推理，生成参数略有不同的新调用

请求 id 每次都是新的，参数哈希也会变。

## 决定

在**规划时**为每个逻辑步骤生成 `step_key = sha256(device_id ‖ plan_id ‖ step_index ‖ tool ‖ identity_args)`，执行前先写进本机 outbox。三跳都用它去重：
- 网关的 `action_ledger`：唯一键是 step_key
- Agent：LangGraph 线程 id 是 `账户:step_key`
- 外部调用：`tool_ledger` 的键是 step_key

`identity_args` 只放决定"是不是同一件事"的业务参数，例如预约的科室和日期，不放备注这类自由文本。这样 LLM 改写了备注，仍然算同一步。

## 后果

- 对比实验（eval/report.md）的 640 个故障回合中，重复副作用率 0%；朴素重试 50%，请求级幂等和参数哈希去重都是 33%。
- 同一个 step_key 带着不同内容到达网关时返回 409。这是故意的：同一步的内容变了，说明出了问题，不能悄悄覆盖。
- 外部系统要能"按 step_key 查询"，否则第③跳"已提交、响应丢失"的情况没法判断。mocks 提供了这个接口；真实系统需要支持幂等键或查询接口。

## 放弃的方案

- **只做请求级幂等**：挡不住重派和重新推理。
- **参数哈希去重**：参数一改就失效。而且即使参数完全相同，也挡不住"已提交、响应丢失"后的重试，消融实验证明了这一点。
- **Temporal / DBOS 这类持久化执行框架**：能解决第②跳。但设备离线排队、跨设备和服务器的同一个键，仍然要自己做；而且会多出一套需要运维的基础设施。
