# 0003 排队的动作执行前先复核，有变化就问用户

状态：已采用

## 背景

离线排队的动作，联网时可能已经不是用户想要的了：
- 号源被别人抢了
- 通知家属"我头晕"晚了 6 小时
- 工具的接口版本变了

只保证"执行一次"还不够，还要保证"执行的是对的事"。

## 决定

每个动作在规划时带上前提条件快照（号源版本、工具契约版本）和 TTL（通知家属 6 小时）。

Agent 图的第一个节点 `revalidate` 是一个纯函数，结果只有三种：照常执行、问用户、取消。
- 问用户用 LangGraph 的 `interrupt()`，线程状态由 checkpointer 保存。
- 客户端显示"需要你确认"和可选项，用户的选择通过 `/resume` 以 `Command(resume=…)` 送回同一个线程。

号源版本变了但仍然有号时，**照常执行**，不打扰用户。"变了"不等于"不对"；误拦率要和拦截率一起看。

## 后果

- 对比实验中，过期和契约变更的动作 30/30 被拦下（基线全部照常执行），仍然有效的动作误拦 0/10。
- 用户的选择本身也走 step_key：恢复时还是同一个线程，不会生成第二个动作。
